**Proyecto:** Sentiment API — Análisis Inteligente de Feedback de Clientes  
**Equipo:** Backend / Data Science  
**Contexto:** Hackathon NoCountry / Alura LATAM  
**Versión:** 1.0

## 1. Contexto General

El presente RFC documenta las decisiones arquitectónicas adoptadas para el desarrollo del sistema **Sentiment API — Análisis Inteligente de Feedback de Clientes**, cuyo objetivo es analizar reseñas de clientes y entregar resultados comprensibles mediante un dashboard.

### 1.1 Condiciones del Proyecto

El proyecto se desarrolla bajo las siguientes condiciones:

- **Uso obligatorio de Java y Spring Boot** para el backend
- **Implementación de arquitectura en capas** según lineamientos de NoCountry
- **Modelo de análisis de sentimiento entrenado en inglés**
- **Dashboard destinado exclusivamente a visualización**

### 1.2 Justificación del RFC

Dado el crecimiento del equipo y la incorporación de nuevos integrantes, se considera necesario dejar registro formal de las decisiones técnicas, su justificación y sus implicancias.

## 3. Arquitectura General del Sistema

### 3.1 Arquitectura en Capas

Se adopta una **arquitectura en capas**, alineada con los requerimientos de NoCountry y validada como una decisión técnica adecuada para este proyecto.

#### Capas Principales

- **Controller**: Manejo de endpoints REST y requests HTTP
- **Service**: Lógica de negocio principal
- **Dominio / Procesamiento**: Entidades y reglas de negocio
- **Infraestructura**: Integraciones externas (BD, servicios DS, etc.)

#### Justificación

- Separación clara de responsabilidades
- Facilita mantenimiento y pruebas
- Escalable ante crecimiento del proyecto
- Compatible con buenas prácticas de Spring Boot

**Nota importante:** Si bien esta arquitectura es un requerimiento externo, se considera que es coherente con los objetivos del sistema y **no se adopta únicamente por obligación, sino por conveniencia técnica**.

Para más detalles sobre la arquitectura, consultar [ARCHITECTURE.md](./ARCHITECTURE.md).

---

### 3.2 Backend como Fuente Única de Verdad

El backend es responsable exclusivo de:

- Validaciones de entrada
- Lógica de negocio
- Procesamiento del análisis de sentimiento
- Interpretación de resultados del modelo
- Generación de mensajes comprensibles para humanos

**Regla fundamental:** El frontend **no toma decisiones de dominio** ni realiza cálculos.

---

### 3.3 Frontend Pasivo (Dashboard)

#### Responsabilidades del Dashboard

- Consume la API
- Visualiza resultados
- Renderiza gráficos y textos

#### Lo que NO contiene

- ❌ Lógica de negocio
- ❌ Validaciones complejas
- ❌ Interpretación de datos

**Justificación:** Esta decisión reduce acoplamiento y facilita cambios futuros.

---

## 4. Patrón de Procesamiento: Chain of Responsibility

Se adopta el patrón **Chain of Responsibility** para manejar validaciones y pasos de procesamiento en backend.

### 4.1 Motivos de la Decisión

- Evitar flujos rígidos basados en `if/else`
- Encapsular responsabilidades individuales
- Facilitar extensión del flujo sin modificar lógica existente
- Mejorar legibilidad y trazabilidad

### 4.2 Ejemplos de Responsabilidades en la Cadena

- Validación de texto vacío
- Validación de longitud (mínima y máxima)
- Detección de idioma (inglés)
- Validaciones previas al análisis del modelo

Cada validador es un eslabón independiente que puede aprobar o rechazar el procesamiento.

---

## 5. Idioma y Exactitud del Modelo

### 5.1 Modelo Entrenado en Inglés

El modelo de análisis de sentimiento está entrenado **exclusivamente con datasets en idioma inglés**.

#### Decisión

- Para garantizar exactitud y confiabilidad de probabilidades, el backend **exige textos en inglés** para ejecutar el análisis
- Textos en otros idiomas son **rechazados con un mensaje explicativo** (código 400)

### 5.2 Responsabilidad de Validación

- La validación de idioma se realiza en el **backend**
- El dashboard puede informar esta limitación, pero **no imponerla**
- La validación es obligatoria antes de enviar el texto al modelo de Data Science

Ver detalles de validación en [API-CONTRACT.md](./API-CONTRACT.md#31-validaciones-requeridas).

## 7. Contrato API

El backend define el **contrato semántico de la API**, incluyendo:

- **Formato de respuesta**: `{"prevision": "...", "probabilidad": 0.x}` (formato obligatorio según especificaciones del cliente NoCountry)
- Categorías de sentimiento (`"Positivo"`, `"Neutro"`, `"Negativo"`)
- Niveles de confianza (probabilidad entre 0 y 1)
- Mensajes explicativos en lenguaje natural (en español)

**Principio:** El frontend consume este contrato **sin reinterpretar los datos**. Toda la lógica de negocio está en el backend.

**⚠️ Importante:** El formato de respuesta debe usar `prevision` y `probabilidad` (en español) según las especificaciones del cliente. Este formato es obligatorio.

Para el contrato completo de la API, consultar [API-CONTRACT.md](./API-CONTRACT.md).

## 8. Selección de Datasets

La selección de datasets es una **decisión crítica** para la calidad del modelo y debe quedar formalmente registrada.

### 8.1 Criterios de Evaluación

Los datasets fueron/serán evaluados según:

- ✅ **Idioma**: Debe ser inglés
- ✅ **Cantidad de muestras**: Suficiente para entrenamiento y validación
- ✅ **Calidad y limpieza**: Datos consistentes y sin ruido excesivo
- ✅ **Relevancia del dominio**: Reseñas, feedback, opiniones de clientes
- ✅ **Licencia y uso permitido**: Compatible con uso en el proyecto

---

### 8.2 Datasets Evaluados

#### 8.2.1 Datasets Descartados

##### Dataset 1: Customer Opinions & Reactions Dataset

| Propiedad | Valor |
|-----------|-------|
| **Fuente** | [Kaggle](https://www.kaggle.com/datasets/ranaghulamnabi/customer-opinions-and-reactions-dataset) |
| **Métricas disponibles** | Serial Number, Age, Gender, Review, Education, Purchased |
| **Resumen** | Contiene reseñas reales de clientes junto con etiquetas de opiniones, valoraciones y patrones de reacción |
| **Ubicación** | Customer_Review (7) en carpeta drive compartida con equipo DS |
| **Motivo de descarte** | ❌ No tenía las reseñas escritas de forma explícita, no cumplía con los requisitos del proyecto |

**Justificación:** Aunque contenía información de opiniones, la falta de textos explícitos de reseñas lo hacía inadecuado para entrenar un modelo de análisis de sentimiento basado en texto.

---

##### Dataset 2: Sentiment Analysis Python (Amazon Reviews)

| Propiedad | Valor |
|-----------|-------|
| **Fuente** | [Kaggle Notebook](https://www.kaggle.com/code/robikscube/sentiment-analysis-python-youtube-tutorial/notebook) |
| **Métricas disponibles** | Row Id, ProductId, UserId, ProfileName, HelpfulnessNumerator, Score, Time, Summary, Text |
| **Resumen** | Reseñas de productos gastronómicos de Amazon. Datos de más de 10 años, aproximadamente 500,000 reseñas publicadas hasta octubre de 2012 |
| **Motivo de descarte** | ❌ Métricas insuficientes para los requisitos del proyecto |

---

#### 8.2.2 Dataset Seleccionado

##### Customer Sentiment Dataset

| Propiedad | Valor |
|-----------|-------|
| **Fuente** | [Kaggle](https://www.kaggle.com/datasets/kundanbedmutha/customer-sentiment-dataset) |
| **Ubicación** | Customer_Sentiment (8) en carpeta drive compartida con equipo DS |
| **Idioma** | Inglés ✅ |
| **Métricas incluidas** | Identificador único del cliente, Género, Grupo de edad, Región geográfica, Categoría de producto, Canal de compra (online, offline, aplicación, sitio web, redes sociales), Plataforma de reseña (Amazon, Flipkart, Meesho, Facebook Marketplace, Myntra, Ajio, Nykaa, Croma, Boat, Reliance Digital, BigBasket, JioMart, Swiggy Instamart, Zepto, etc.), Valoración numérica (1-5), **Texto de la reseña escrito por el cliente**, **Etiqueta de sentimiento (positivo, negativo, neutro)**, Tiempo de respuesta, Estado de resolución, Registro de quejas |

**Resumen:** Este conjunto de datos refleja cómo los clientes expresan sus experiencias en múltiples plataformas de comercio electrónico. Captura un amplio espectro de opiniones, desde clientes muy satisfechos que elogian la calidad del producto y la rapidez de la entrega, hasta usuarios insatisfechos que informan de problemas como retrasos en las entregas, artículos de baja calidad o una atención al cliente insatisfactoria.

**Clasificación de sentimiento:**
- Calificaciones 4-5 → Opiniones **positivas**
- Calificación 3 → Opiniones **neutras**
- Calificaciones 1-2 → Opiniones **negativas**

Cada reseña incluye el texto escrito por el cliente y la etiqueta de sentimiento correspondiente, lo que hace que el conjunto de datos sea ideal para la comprensión del texto y el análisis de opiniones.

---

### 8.3 Justificación de la Selección

El **Customer Sentiment Dataset** fue seleccionado porque cumple con todos los criterios establecidos:

1. ✅ **Idioma inglés**: Todas las reseñas están en inglés
2. ✅ **Texto explícito**: Incluye el texto completo de las reseñas escritas por los clientes
3. ✅ **Etiquetas de sentimiento**: Clasificación clara (positivo, neutro, negativo)
4. ✅ **Relevancia del dominio**: Reseñas de clientes sobre productos y servicios
5. ✅ **Múltiples plataformas**: Diversidad en las fuentes de datos
6. ✅ **Métricas adicionales**: Información complementaria útil para análisis

## 9. Principios de Diseño y Clean Code

Se adopta explícitamente los siguientes principios:

### 9.1 Principios Aplicados

- **Principio de Responsabilidad Única (SRP)**: Cada clase tiene una única razón para cambiar
- **Separación clara de capas**: Cada capa tiene responsabilidades bien definidas
- **Clases con responsabilidades bien definidas**: Sin ambigüedades sobre qué hace cada componente
- **Métodos pequeños y expresivos**: Código legible y fácil de entender
- **Evitar lógica duplicada**: DRY (Don't Repeat Yourself)
- **Documentación clara**: Cada archivo debe estar documentado apropiadamente

### 9.2 Objetivos de estas Decisiones

- ✅ Código mantenible
- ✅ Facilidad de testing (unit tests, integration tests)
- ✅ Claridad para nuevos integrantes
- ✅ Escalabilidad del proyecto

## 10. Alternativas Consideradas y Descartadas

Durante el diseño del sistema se consideraron las siguientes alternativas, que fueron descartadas por las razones indicadas:

### 10.1 Alternativas Descartadas

| Alternativa | Motivo de Descarte | Consecuencias Evitadas |
|-------------|-------------------|------------------------|
| **Lógica distribuida entre frontend y backend** | Mayor acoplamiento, dificulta mantenimiento | ❌ Duplicación de lógica<br>❌ Inconsistencias entre frontend y backend<br>❌ Dificultad para hacer cambios |
| **Validaciones en controllers** | Violación de principio de responsabilidad única | ❌ Controllers sobrecargados<br>❌ Dificultad para reutilizar validaciones<br>❌ Testing más complejo |
| **Flujo monolítico con if/else** | Código rígido y difícil de extender | ❌ Mantenimiento complicado<br>❌ Menor claridad<br>❌ Dificultad de evolución |

### 10.2 Decisión Final

Se optó por la arquitectura actual (capas + Chain of Responsibility + backend como fuente de verdad) porque ofrece:

- ✅ Menor acoplamiento
- ✅ Mayor claridad y mantenibilidad
- ✅ Facilidad de evolución y extensión
- ✅ Mejor testabilidad

## 11. Decisiones Registradas en este RFC

Este documento deja constancia formal de las siguientes decisiones arquitectónicas:

1. ✅ **Arquitectura en capas** (Controller, Service, Domain, Infrastructure)
2. ✅ **Backend como fuente única de verdad** para lógica de negocio
3. ✅ **Frontend pasivo** (solo visualización, sin lógica de negocio)

7. ✅ **Selección de dataset** (Customer Sentiment Dataset)
8. ✅ **Aplicación de principios de clean code** y responsabilidad única

## 12. Impacto y Consecuencias

### 12.1 Impacto Positivo

- **Mantenibilidad**: Código organizado y fácil de mantener
- **Escalabilidad**: Estructura que permite crecer sin problemas
- **Testabilidad**: Separación clara facilita escribir tests
- **Onboarding**: Nuevos integrantes entienden la arquitectura rápidamente
- **Calidad**: Validaciones centralizadas garantizan consistencia

### 12.2 Limitaciones Aceptadas

- **Idioma único**: Solo procesa textos en inglés (limitación del modelo)
- **Arquitectura rígida**: Requiere seguir estructura en capas (compensado por beneficios)
- **Backend centralizado**: Toda la lógica en backend puede crear un punto único de falla (mitigado con buenas prácticas de código)
